# ADR 0004：版本化设置与迁移

- 状态：已接受
- 日期：2026-10-19
- 决策者：项目维护者
- 相关文档：[数据与迁移](../data-and-migrations.md)、[架构设计](../architecture.md)

## 背景

插件会持续增加特性和设置项。用户配置保存在 `data.json`，需要在多个版本之间保持可用。

常见问题：

- 新版本增加选项，旧配置缺少字段；
- 选项重命名或类型变化；
- 特性 ID 变化；
- 用户降级插件，数据包含新字段；
- `data.json` 被手工编辑或损坏；
- 保存过程中崩溃，导致写入不完整。

如果没有版本和迁移机制，只能让用户重新配置，或者写一次性兼容代码，最终难以维护。

## 决策

采用单一 `data.json` + 显式版本 + 顺序迁移：

```ts
interface PluginData {
  schemaVersion: number;
  global: GlobalSettings;
  features: Record<string, {
    enabled: boolean;
    options: Record<string, unknown>;
  }>;
}
```

规则：

- 开关与选项分离：`enabled` 不在 `options` 内。
- 加载时合并默认值；新增选项不需要迁移。
- 保存时写入当前有效值；默认值调整不自动覆盖老用户已有值。
- 未知特性块、未知选项键、未知全局键保留，支持降级和特性恢复。
- 迁移按 `schemaVersion` 顺序执行；版本高于当前时不迁移。
- 迁移失败记录错误并回退默认数据，不写入半迁移结果。
- 迁移函数必须是纯函数，并有旧版本 fixture 测试。
- 保存防抖 300ms；开关立即 `flush()`；写盘串行化。
- 不在 `data.json` 保存密钥；未来使用 SecretStorage。

## 结果

### 正面

- 升级不丢配置，破坏性变更可测试。
- 新增设置零迁移。
- 降级不会立即删除新版本写入的数据。
- 保存失败不会破坏内存状态。
- 数据格式和迁移历史可审计。

### 负面 / 代价

- 每次破坏性变更都要写迁移和测试。
- 单文件保存会重写整个配置；特性很多时写放大。
- 默认值调整不会自动影响老用户，需要迁移才能强制更新。
- 未知键保留可能让数据逐渐臃肿。

## 备选方案

### 每个特性一个文件

隔离性好，但：

- 多文件写入难以保证原子性；
- 插件需要自己管理目录和并发；
- Obsidian `loadData`/`saveData` 的便利性丧失；
- 迁移和备份更复杂。

### 无版本，只做字段兼容

短期简单，长期会积累大量 `if (oldField)` 分支；无法判断数据来自哪个版本，也无法安全清理。

### 只保存与默认值的差异

可以让默认值变更自动传播，但：

- 需要区分“用户显式设置为默认值”和“未设置”；
- 迁移和调试更复杂；
- 对当前规模收益有限。

### 外部数据库 / IndexedDB

增加复杂度和备份问题，不适合插件配置。

## 重新评估条件

- 数据规模增大到单文件写入明显卡顿；
- 需要按工作区或设备同步不同配置；
- 需要存储大体积结构化数据（不适合 `data.json`）；
- Obsidian 提供更合适的配置存储 API。
