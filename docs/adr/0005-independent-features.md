# ADR 0005：特性互相独立

- 状态：已接受
- 日期：2026-10-19
- 决策者：项目维护者
- 相关文档：[架构设计](../architecture.md)、[生命周期](../lifecycle.md)、[新增特性](../feature-development.md)

## 背景

多特性插件很容易演变成依赖网络：

- 特性 B 导入特性 A 的工具函数；
- 特性 C 需要特性 A 启用才有意义；
- 关闭 A 时，B、C 的行为变得不确定；
- 启动顺序、级联开关、循环依赖需要额外机制。

一旦引入依赖，用户关闭一个特性就可能产生连锁反应，设置页也要解释“为什么这个开关是灰的”，维护成本迅速上升。

## 决策

特性之间保持独立：

- `features/<id>/` 不得导入其他特性目录；
- 不声明 `dependsOn`、`requires` 或启动顺序；
- 跨特性共享的纯逻辑放 `src/lib/`；
- 如果两个特性需要共享状态，先判断是否应该合并为一个特性，或把状态提升为插件级服务；
- 生命周期只保证单个特性的启用/关闭，不做级联；
- ESLint/review 禁止特性间导入。

允许的共享：

- `core/feature.ts` 中的类型；
- `lib/` 中的无状态工具；
- `i18n` 文案；
- Obsidian API。

不允许的共享：

- 直接导入另一个特性的模块；
- 通过全局变量/事件总线交换状态；
- 一个特性假设另一个特性已启用。

## 结果

### 正面

- 每个特性的启停互不影响，用户可预测。
- 生命周期简单：只管理自己的资源。
- 测试独立：不需要构造其他特性。
- 注册表顺序不影响正确性。
- 设置页不需要表达依赖关系。

### 负面 / 代价

- 可能出现重复代码，需要主动提炼到 `lib/`。
- 真正需要协作的功能可能被迫合并，或通过插件级服务实现。
- 没有统一的事件总线，特性间通信要靠显式设计。

## 备选方案

### 依赖声明 + 拓扑排序

```ts
requires: ['feature-a'];
```

可以实现，但需要：

- 循环检测；
- 启用顺序；
- 关闭时级联或阻止；
- UI 表达依赖；
- 依赖特性的失败传播。

对当前规模来说复杂度大于收益。

### 服务容器 / 事件总线

提供松耦合通信，但也让依赖变得隐式：特性 B 可以运行时才依赖 A，静态分析无法发现。对插件规模而言，显式合并或提升为插件级服务更清晰。

### 单一“大特性”

把所有功能塞进一个模块，确实没有依赖问题，但失去独立开关和独立配置的能力，违背需求。

## 重新评估条件

- 出现多个特性共享同一份有状态服务，且无法提炼为无状态 `lib/`；
- 用户明确需要“启用 A 才能使用 B”的产品语义；
- 特性数量增长到必须分组管理；
- 需要第三方特性扩展生态。
